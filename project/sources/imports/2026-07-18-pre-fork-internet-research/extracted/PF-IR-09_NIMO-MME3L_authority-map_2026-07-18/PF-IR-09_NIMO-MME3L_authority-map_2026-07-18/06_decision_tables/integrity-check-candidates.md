# Integrity Check Candidates

| candidate | detects | does_not_cover | implementation_evidence | priority | status |
| --- | --- | --- | --- | --- | --- |
| Btrfs/ZFS data+metadata checksums with scheduled scrub and redundant repair source | Persistent block/path corruption within protected filesystem scope | Transient CPU/GPU execution corruption; unprotected volumes; corruption copied before checksum | Checksum mode, redundancy, scrub schedule, alert test, restore drill | P1 when storage/RAM RAS absent | Candidate compensating control |
| dm-integrity, optionally with authenticated encryption | Block-level integrity mismatch/torn writes in configured mapping | Corruption above the block layer; all transient computation errors | Tag mode, journal mode, key management, performance validation, recovery test | P2 | Candidate |
| Application artifact hashes and signed manifests | Changed model weights, binaries, datasets, firmware files and configuration artifacts | In-memory corruption after verification unless rechecked | SHA-256/stronger manifests, signer trust, verify-on-load and periodic recheck | P1 | Recommended |
| fs-verity for immutable files | On-read modification/corruption of protected files | Mutable data and runtime memory errors | Enabled files, root hash provenance, enforcement and alert path | P2 | Candidate |
| IMA appraisal/measurement plus TPM-backed measured boot | Unexpected executable/config changes and boot-chain measurement drift | Physical faults producing transient correct execution-path corruption | Policy, key chain, TPM quote baseline, verifier, failure behavior | P1 for firmware trust gap | Recommended candidate |
| Database page checksums, consistency checks and verified replicas | Page/log corruption and logical inconsistency within database scope | Identical corruption propagated to replicas or undetected computation errors | Checksum enabled, validation cadence, replica independence, restore drill | P1 for critical data | Recommended |
| Object-store content addressing and cross-node hash comparison | Replica/content divergence | Common-mode corruption before hashing | Independent hash calculation, quorum/repair logic, audit logs | P2 | Candidate |
| GPU/CPU result validation: deterministic canaries, redundant execution, bounds/invariant checks | Some silent computation errors and driver/firmware regressions | Errors that preserve checked invariants or affect both redundant paths identically | Golden outputs, cadence, independent execution path, fail-closed policy | P1 for safety/financial/scientific workloads | Recommended candidate |
| Read-only firmware and package inventory with recurring hashes | Unexpected changes to BIOS-reported versions, linux-firmware files, initramfs, drivers and fwupd metadata | Authenticity without trusted reference; hidden device firmware changes | Trusted baseline, signed report, recurring collection, alerting | P1 | Recommended |
| pstore/ramoops, persistent journal and remote log shipping | Preserves pre-crash AER/MCA/EDAC/amdgpu/NVMe evidence | Silent errors that produce no log; log loss before persistence | Reserved storage, crash test, remote receipt and retention | P1 for telemetry gap | Recommended |
| Periodic offline memory/storage diagnostics with known-good images and hashes | Some reproducible memory, media and controller failures | All intermittent faults; destructive tests may alter state | Non-destructive test plan, maintenance approval, baseline and trend | P2 | Candidate; human-approved only |
| Immutable deployment images and signed rollback bundle | Configuration/package drift and enables deterministic recovery | Hardware faults or vulnerable firmware retained in image | Image digest, SBOM, signing key, alternate boot and restore test | P1 | Recommended |
