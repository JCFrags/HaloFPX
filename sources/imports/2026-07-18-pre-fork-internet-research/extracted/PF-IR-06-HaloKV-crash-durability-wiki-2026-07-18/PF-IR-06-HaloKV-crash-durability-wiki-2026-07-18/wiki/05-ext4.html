ext4 profile

Realistic profile

ext4 is the provisional baseline only because the deployed filesystem was not identified. The candidate profile is local ext4 with data=ordered, delayed allocation as provided by the default profile, write barriers enabled, and explicit application file+directory synchronization.

Material semantics

  • data=ordered writes associated data before committing related metadata, but it does not make arbitrary completed writes durable without synchronization.
  • delayed allocation means blocks can remain dirty without physical allocation until writeback; ENOSPC can be deferred.
  • auto_da_alloc detects common broken replace/truncate patterns to reduce zero-length crash outcomes. It is explicitly not a substitute for the application protocol.
  • data=writeback does not preserve data-before-metadata ordering and is denied by the proposed persistent profile.
  • data=journal disables delayed allocation and O_DIRECT. A deployment using it needs a different performance and DIO profile.
  • barriers must remain enabled unless the complete cache and power-loss path is independently nonvolatile and tested. nobarrier is denied by default.
  • errors=remount-ro is operationally useful, but the application must still detect EROFS/EIO and fence the root.

ext4-specific optimizations that do not change the portable minimum

fallocate, larger files, directory layout and batching can improve allocation or amortize sync cost. None removes exact-write validation, file sync, atomic publish, directory sync, and fault testing.

Required ext4 matrix

Run T007–T022, T023–T026 if using DIO, T038, and T040 on the exact ext4 feature/mount profile. Include data-block exhaustion, inode/metadata exhaustion, journal replay after host power cut, overwrite, create collision and directory-sync failure.
